## 卡死证据与处理

- 原Air build106的CPU报告：约104秒内90秒CPU（86%），另有主线程无法按时退出的watchdog报告。
- 真机Time Profiler显示主线程在ViewGraph.updateOutputs / beginNextUpdate / graphInvalidation间持续循环，并出现TimelineView.UpdateFilter；没有证据表明在等待学校网络。原页与工具栏同时包装动态TimelineView，并在渲染时订阅/拼装多种业务组件，证据指向这一组合与导航转场形成渲染失效反馈。未将Apple框架内部每个步骤逐行归因为某一业务函数。
- 修复移除通知页与工具栏TimelineView；消息由独立Store在业务事件和本地时间边界产生，页只渲染最多200条持久记录；不在进入通知时刷新学校服务器。入口统一CampusDetail.inbox，避免消息跳转混用布尔导航与路径导航。
- 同一Air后续约10秒采样，beginNextUpdate样本从7596降至38；原采样约11.5秒，两个窗口场景不同，因此只作为持续循环消失的旁证，不换算严格CPU性能倍数。脱敏汇总见profile-summary.json；原始个人设备日志留在本机/tmp，未提交。

## 消息行为

- 作业与考试仍合并每日提醒；纯考试提醒跳考试页，含作业摘要跳作业页；保留31/14/7/3天考试里程碑。
- 系统送达、前台接收、点击均进入同一事件记录，以系统标识去重。登录只在确认需要重新登录时提醒，同一次失效跨启动去重；预约进入六小时窗口时生成一次。
- 消息更新复用缓存及已有采集回调，前台本地每分钟检查时间边界，未新增学校请求。历史消息与当前业务状态分开，重新登录或完成作业不会改写已发生的通知历史。
- 系统通知送达、后台唤醒仍由iOS控制；本轮未逐项等待真实考试日期或预约开始时间。
