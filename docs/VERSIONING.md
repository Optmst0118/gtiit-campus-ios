# 版本号规则

本项目的对外版本采用 主版本.功能版本.修订版本，例如 2.0.1。

## 版本递增

| 更新类型 | 版本变化 | 适用情况 |
| --- | --- | --- |
| 小修复、优化 | 2.0.1 → 2.0.2 | 崩溃修复、配色/布局调整、动画/触感优化、性能提升、兼容性修复 |
| 功能更新 | 2.0.2 → 2.1.0 | 新增用户实际可用的功能，或明显扩展现有功能 |
| 重大版本 | 2.1.3 → 3.0.0 | 产品定位、核心使用方式或主要功能体系发生重大变化；普通重构不算 |

规则：

- 高位递增，低位归零。
- 按实际交付判断，内部重构不算功能更新。
- 同一轮交付同时包含新功能与修复时，按功能更新计。
- 一次交付只升一次；开发中的反复编译、验证不重复增加对外版本号。
- 相同代码重新安装、重新签名不升级版本。

## 测试阶段

- 2.1.0-alpha.1：功能仍在开发，可能不完整。
- 2.1.0-beta.1：功能基本完成，进入验证。
- 2.1.0-rc.1：候选正式版，只处理发布前问题。
- 2.1.0：正式版。

## Build 号

Build 独立、全局递增，不随版本号归零。用于区分实际安装包。

示例：

- 2.0.2-beta.1（build 65）修复与界面优化
- 2.0.2-beta.2（build 66）同一版本继续测试
- 2.0.2（build 67）正式发布
- 2.1.0-beta.1（build 68）下一次新增功能

## 当前边界

- 已交付的 2.0.1-beta（当前代码基线 build 69）作为规则生效前的历史记录保留，不追改历史。
- 下一次**实际代码交付**：
  - 只有修复/视觉优化：2.0.2-beta.1（build 70 起）
  - 含新增用户功能：2.1.0-beta.1（build 70 起）
- 同一轮交付不重复递增；正式版发布时填写对应 2.0.2 或 2.1.0，prerelease 为空。

## 代码/数据约定

- Tools/version.json 的 marketing 必须是三段式数字。
- prerelease 使用 alpha.N / beta.N / rc.N；正式版为空字符串。
- build 是全局递增整数。
- 修改版本后重新运行 Tools/gen_project.py 和 Tools/check_project.py。
- AppInfo.versionText 使用 GTIIT_RELEASE_LABEL + build；正式版不带尾部连字符。
